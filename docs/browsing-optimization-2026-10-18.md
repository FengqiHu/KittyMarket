# 商品浏览分页改造与复测（2026-10-18）

买家首页原先一次读取全部 5026 件商品，响应约 3,162,138 字节，再在浏览器中按每页 8 件切片。首页已改为调用 `GET /good/buyer-goods-page?category=全部&page=1&size=8`：数据库按分类、商品 ID 和页码返回当前页，以及该分类的总数。旧的完整列表接口保留；买家登录响应中前端未使用的完整商品列表已移除。

新接口首屏返回 8 件商品、约 3,466 字节，比原接口减少约 99.89% 的响应体积。核对了两页商品无重复、总数仍为 5026、主粮分类总数为 1733 且商品分类正确，非法页码返回 HTTP 400。前端 lint 和生产构建通过。

使用同一台机器和数据库，从同一台机器发起只读 HTTP 长连接请求。通过条件与上次相同：错误率不超过 1%，P95 响应时间不超过 1000 毫秒，每个工作线程至少完成 2 次请求。

| 接口 | 并发请求 | 测试轮次 | P95 响应时间 | 错误 | 吞吐量 | 结果 |
| --- | ---: | --- | --- | ---: | --- | --- |
| 原完整列表接口 | 48 | 10 秒 × 2 | 998 / 929 毫秒 | 0 / 0 | 约 58 次/秒 | 两轮通过，接近阈值 |
| 原完整列表接口 | 50 | 10 秒 × 2 | 1026 / 980 毫秒 | 0 / 0 | 约 57 次/秒 | 一轮超过阈值 |
| 新分页接口 | 256 | 10 秒 × 2 | 141 / 145 毫秒 | 0 / 0 | 7330 / 6998 次/秒 | 两轮通过 |
| 新分页接口（主粮分类） | 256 | 10 秒 × 2 | 220 / 185 毫秒 | 0 / 0 | 4691 / 5653 次/秒 | 两轮通过 |

**首次复测确认新接口至少支持 256 个并发请求，当时达到测试上限；下文记录了继续向上探测的结果。** 与旧接口已验证的 48 并发相比，首次复测的已验证档位提高至少约 5.3 倍。新旧接口的响应体积不同，因此吞吐量不能直接当作服务器整体处理能力的等比例提升。此次测试测量的是独立 API 请求，未覆盖完整浏览器页面、图片、网络链路或多服务部署。

## 更高并发复测（添加数据库索引前）

同日继续向上探测时，原 Python 线程脚本在 832 并发的两轮 10 秒测试中通过，但 840 并发有一轮超出 P95 门槛。交叉检查发现其高并发结果受客户端线程和连接管理影响：ApacheBench 在 1920 并发完成一轮 7 万次请求（P95 382 毫秒、0 错误），但后续测试因本机临时端口耗尽而中止。故不能把这些客户端失败解释为服务端容量上限。

改用支持 HTTP 长连接的 Node 压测脚本，确认每档实际在途请求峰值和建立的连接数都达到目标并发；两轮测试之间等待本机 `TIME_WAIT` 端口回收。每轮持续 10 秒，校验 HTTP 200、JSON 结构及 `page=/buyer`，仍以错误率不超过 1%、P95 不超过 1000 毫秒为通过条件。

| 并发请求 | P95 响应时间 | 错误 | 结论 |
| ---: | --- | ---: | --- |
| 4096 | 644 毫秒 | 0 | 单轮通过 |
| 5120 | 795 毫秒 | 0 | 单轮通过 |
| 5376 | 910 / 864 毫秒 | 0 / 0 | 两轮通过 |
| **5504** | **925 / 889 毫秒** | **0 / 0** | **两轮通过，最高已验证档位** |
| 5568 | 1021 毫秒 | 0 | 超过 P95 门槛 |
| 5632 | 974 / 1032 毫秒 | 0 / 0 | 一轮超过门槛 |
| 6144 | 1294 毫秒 | 0 | 超过 P95 门槛 |

**添加索引前，按上述本机 API 测试标准，最高重复通过的是 5504 个并发请求。** 这不是服务端精确的物理极限，也不等于可同时服务 5504 个完整浏览器用户；5504 档位距离 1 秒 P95 门槛已经很近。压测机与后端、MySQL 同机，压测机自身也会争用 CPU 和网络资源。

复测最高通过档位：

```sh
node scripts/benchmark_browsing_keepalive.cjs 5504 10
node scripts/benchmark_browsing_keepalive.cjs 5504 10
```

大量连接结束后会占用本机临时端口一段时间；复测高并发档位前应等待 `TIME_WAIT` 连接回收。若出现 `EADDRNOTAVAIL`，该轮反映的是压测机端口耗尽，不能计为服务端失败。

复测命令：

```sh
python3 scripts/benchmark_concurrency.py --url 'http://127.0.0.1:8080/good/buyer-goods-page?page=1&size=8' --expected-page /buyer --start-concurrency 256 --max-concurrency 256 --duration 10 --repeats 2 --timeout 10
```

## 数据库索引（添加后复测）

`MLgood` 新增 `(state, goodid)` 和 `(state, kind, goodid)` 索引。建表语句和已有数据库的幂等迁移均已加入 `schema.sql`；本机已执行迁移两次并运行 `ANALYZE TABLE MLgood`，启动时再次执行迁移也通过。

添加前，`EXPLAIN` 显示全部商品与分类商品的计数都扫描整张表；添加后，两者分别使用对应的覆盖索引，分类分页也使用 `(state, kind, goodid)`。一次 `EXPLAIN ANALYZE` 样本中，全部商品计数约从 3.04 毫秒降为 0.99 毫秒，主粮分类计数约从 3.28 毫秒降为 0.79 毫秒。单次查询时间受缓存影响，不能当作稳定的延迟保证。

同一 Node 客户端在主粮分类、256 并发下测得：添加前两轮 P95 为 168 / 165 毫秒、吞吐量约 5884 / 5950 次每秒；添加后预热的两轮 P95 为 105 / 102 毫秒、吞吐量约 9457 / 9434 次每秒。添加后首轮较慢（P95 327 毫秒），说明整体压测结果存在明显的缓存和运行状态波动。

首页“全部商品”在添加索引后，4096 并发两轮通过（P95 889 / 595 毫秒，均 0 错误），5504 并发两轮未通过（P95 1117 / 1461 毫秒，均 0 错误）。**索引已改善计数与分类查询的执行计划，但本次数据不能证明首页最大并发数提高；先前的 5504 是添加索引前的测量值。** 高并发档位的端到端延迟还受 JVM、MySQL、压测机和连接状态影响。
